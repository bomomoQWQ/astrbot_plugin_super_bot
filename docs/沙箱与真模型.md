## 一、沙箱：Shipyard Neo（Bay）

### 1. 部署（Docker Compose）

```powershell
cd F:\Astrbot-Super-Bot\.runtime\shipyard-neo\deploy\docker
# 1) 改 config.yaml 里的 security.api_key（换成自己的强随机串）
# 2) 起
docker compose up -d
# 3) 健康
curl http://localhost:8114/health      # {"status":"ok","version":"0.4.2"}
```

- Bay 监听 **8114**（`0.0.0.0:8114->8114`），Gull（浏览器运行时）走内网。
- 镜像：`ghcr.io/astrbotdevs/shipyard-neo-{bay,ship,gull}:latest`，首次会拉取。
- 数据卷 `bay-data`（SQLite）+ 绑定挂载 `./bay-cargos`（Cargo 工作区）。

### 2. API key 放哪

`config.yaml` 里 `security.api_key` 就是它。本地测试脚本会读
`.runtime/bay_key.txt`（或环境变量 `BAY_API_KEY`）。

> **坑 1（踩过）**：PowerShell 5.1 的 `Set-Content -Encoding utf8` 会写 **BOM**。
> 带 BOM 的 key 会被 Bay 判成 401 `Invalid API key`——因为 BOM 被当成了 key 的一部分。
> 读的时候一律用 `utf-8-sig`，写的时候用 `UTF8Encoding($false)`。
>
> **坑 2（踩过）**：Bay 首次启动会把 key 的 hash 写进 `bay.db`，之后**只认 DB 里的那把**。
> 你改了 `config.yaml` 的 api_key 却只是 `restart`，会一直 401。要么 `docker compose down -v`
> 清卷重来，要么把容器里的 `/app/data/credentials.json` 读出来用。

### 3. 验证（不经过 AstrBot，直接打 API）

```powershell
cd F:\Astrbot-Super-Bot
python -m tests.e2e.sandbox_smoke
```

8 项断言：健康 → 创建沙箱 → 执行 Python → 写文件 → 读回 → 执行 Shell → 销毁。

单测层还有两条 `live` 用例（默认跳过）：

```powershell
python -m pytest tests/test_sandbox.py -m live -q -o addopts=""
```

其中 `test_live_sandbox_isolation_between_sandboxes` 专门验证**两个沙箱互不可见**——
这正是「一个 Ticket 一个沙箱」要的隔离。

### 4. 插件里怎么用

`superbot/sandbox.py` 提供 `SandboxPort`（协议）与 `BaySandbox`（HTTP 实现）。
Worker 在 `SUPERBOT_SANDBOX=1` 时走沙箱，否则走桩：

```powershell
$env:SUPERBOT_SANDBOX=1
$env:BAY_ENDPOINT="http://localhost:8114"
$env:BAY_API_KEY="sk-bay-..."
```

**两条必须自己做的事**（AstrBot 全仓库从不调用它们）：

| 事 | 为什么 |
|---|---|
| `keepalive` / `extend_ttl` | 沙箱 TTL 默认 3600s，到期后 managed Cargo **级联删除** → 工作区没了。`superbot/sandbox.py::keepalive_loop` 就是干这个的 |
| `destroy` | `task.cancel()` 只停了客户端 await，容器还在跑并占配额。Worker 的 `finally` 里必须 destroy |

### 5. 为什么不用 AstrBot 的 `get_booter()`

它的隔离粒度是 **UMO** 而不是 Ticket、endpoint/token 只能读全局配置、
无空闲回收、还会污染共享的 `session_booter`（详见
[调查/05-sandbox.md](调查/05-sandbox.md)）。自己直连 Bay 才能「一个 Ticket 一个沙箱」。

### 6. 观察到的行为（不是 bug）

`docker ps` 会看到若干 `bay-session-*` 容器常驻——那是 Bay 的**预热池**
（`warmup_worker`，日志里 `warm_state`/`warm_rotate_ttl=1800`），不是我们泄漏的沙箱。
`GET /v1/sandboxes` 返回 0 才说明用户沙箱都清干净了。
不想让它占资源就调 `config.yaml` 的 `warm_pool_size`。

## 二、真模型：复用本机已有凭据

### 能复用吗？——能，但要换端点

本机 `~/.dsh/.credentials.yaml` 里存着三把 key：

| 名字 | 说明 |
|---|---|
| `DEEPSEEK_API_KEY` | DeepSeek 官方，**可用** |
| `BOMOMO_API_KEY` | 当前 DSH 会话走的自建中转（`https://144.34.155.213:8443/v1`），**本机连不通（握手超时）** |
| `OLLAMA_API_KEY` | ollama.com |

所以「复用我现在用的模型」的落地方式是：**用同一把 `DEEPSEEK_API_KEY`，指向官方端点**
`https://api.deepseek.com/v1`，模型 `deepseek-flash`（DeepSeek-V4-Flash，与我当前同一族）。

实测 `GET /v1/models` 返回：`['deepseek-flash', 'deepseek-v4-pro']`。

### 怎么接

`tests/e2e/harness.py` 里有 `deepseek_provider()` / `config_with_real_model()`，
从 DSH 凭据里读 key（**不打印、不落盘**），生成 AstrBot 的 provider 配置：

```python
{"id": "deepseek-live", "provider": "openai", "type": "openai_chat_completion",
 "provider_type": "chat_completion", "enable": True, "key": ["sk-..."],
 "api_base": "https://api.deepseek.com/v1", "model": "deepseek-flash"}
```

### 验证


`live_chain` 实测回复：

> `暂时没有特别的新鲜事，有新消息我会同步。（沙箱 6×7=42）`

前半句来自**真模型**，括号里来自**真沙箱**——一句话同时证明两条外部依赖都进了主流程。

## 三、插件里新增的两个环境开关

| 变量 | 取值 | 作用 |
|---|---|---|
| `SUPERBOT_EVAL_MODE` | `ignore` / `echo` / `live` | Router 的评估器。`live` 走 `Context.tool_loop_agent` 调真模型 |
| `SUPERBOT_SANDBOX` | `1` | Worker 在真沙箱里执行；否则走桩 |
| `BAY_ENDPOINT` | `http://localhost:8114` | Bay 地址 |
| `BAY_API_KEY` | `sk-bay-...` | 也可从 `.runtime/bay_key.txt` 读 |

**`live` 评估器刻意不给工具**（`max_steps=1`）：Router 只判断与分派，不自己执行（ADR-02）。
需要身份载体时用 `superbot/synthetic.py` 造的合成事件（照抄 `CronMessageEvent` 67 行）——
它是 `superbot/` 包里唯一依赖 astrbot 的模块。
