## 三个坑（都踩过了）

### 1. Python 3.13 缺 `audioop`

AstrBot 的 `.python-version` 是 3.12，但 3.13 移除了 `audioop`（PEP 594），
`astrbot/core/utils/tencent_record_helper.py:4` 会直接 ImportError。

```powershell
python -m pip install audioop-lts
```

（`requirements.txt` 里也有这行，带 `python_full_version >= '3.13'` 环境标记。）

### 2. OneBot 反向 WS 的握手头是**必需**的

`aiocqhttp/__init__.py:506` 直接读 `X-Client-Role`，**没有默认值**；缺了就 400。

```
X-Self-ID: 10000              # 机器人自己的 QQ 号
X-Client-Role: Universal      # 只认 event / api / universal
Authorization: Bearer <token> # 仅当配置了 ws_reverse_token
```

端点：`/ws`（universal）、`/ws/event`、`/ws/api`（`aiocqhttp/__init__.py:140`）。
我们用 `/ws` + `Universal`，同一条连接既发事件也收 API 回执。

### 3. 首次启动会刷几百行 `Config key missing`

那是 AstrBot 在把缺失的配置项从 `DEFAULT_CONFIG` 补齐（`config/astrbot_config.py:93`），
属正常现象，只发生一次。

## 假模型的可控指令

在消息里带上标记，假模型会给出可断言的回复：

| 标记 | 行为 |
|---|---|
| `[[echo:TAG]]` | 回复 `ECHO:TAG`（证明模型确实被调用、且上下文到了） |
| `[[slow:秒]]` | 延迟再回（测超时 / 取消） |
| `[[tool:工具名]]` | 返回一个 tool_call（测工具循环，后续启用） |

`FakeLLM.call_count` 可直接断言"模型被调了几次"——
这是验证"普通群聊不进模型"的关键指标。

## 已验证的行为（8 项）

1. 插件加载并初始化（日志有 `[super-bot] initialized`）
2. 普通群聊（无 @）→ Gate 判定 `route`，写进 `disposition`
3. 普通群聊 → **没有**任何发送动作
4. 普通群聊 → **没有**调用模型（`call_count == 0`）
5. `/help` → 放行给原生流程，有回复
6. `@机器人` → 唤醒主 agent → 拿到模型回复
7. 模型确实被调用
8. 机器人自己的消息 → `ignore`，不回环

## e2e 入口一览

| 脚本 | 验什么 | 断言数 |
|---|---|---|
| `python -m tests.e2e.smoke` | **原生链路**：指令 / @ 唤醒 / 不回环 / 不进模型 / `/sb` 状态 | 13 |
| `python -m tests.e2e.scenarios` | **我们自己的链路**：Gate → Router 批处理 → Worker → Outbox → 发送；以及 `/stop` | 22（batching 12 + stop 10） |
| `python -m tests.e2e.config_path` | 只靠 Dashboard 配置文件（不设任何环境变量）能否工作 | 4 |
| `python -m tests.e2e.watchdog` | 卡住 → 判停滞 → 重试 → 升级 → 判死 + 通知 | 12 |
| `python -m tests.e2e.direct` | `/sb` 子命令、`/sb do` 直通 Worker、模型走工具派活 | 15 |

`scenarios` 的 `batching` 场景依赖两个环境变量（harness 会替我设）：

| 变量 | 作用 |
|---|---|
| `SUPERBOT_EVAL_MODE=echo` | 桩评估器对带 `sb:` 的消息开工单 |
| `SUPERBOT_EVAL_DELAY=1.0` | 假的模型耗时 —— **评估期间的合并窗口就是它** |

### batching 场景验证了什么

1. 三条同 Thread 消息突发 → **只评估一次、batch=3、只回一条**
2. 不带 `sb:` 的三条同样被合并成一批（评估了，但不说话）→ 不刷屏
3. Router 开了工单并派工（日志 `ticket .../dispatched`）
4. **Worker 真的执行完并回话**（日志 `worker done`）——证明不是 Router 直接回
5. 两个不同群（不同 Thread）各自成批、各自回复、发到各自的群

### 为什么需要 `coalesce` 窗口

"单槽 + 只追加"能保证**评估进行期间**到达的消息自动合并；但**第一条消息不会等**，
它一到就开跑。真实 Router 因为一直在忙别的事，天然有延迟；空闲的 Router 就需要
一个很短的窗口（`Router.coalesce`，默认 150ms）把同一瞬间到达的几条聚成一批。

这个窗口只在"从空闲转入忙碌"时生效，评估进行中不需要它。
