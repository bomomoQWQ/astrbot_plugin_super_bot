## 1. 三个决定性发现（读源码才拿得到，直接改变设计）

### 1.1 插件 handler 本身就是唤醒源 —— WakingCheck **不会**挡你

先前的担心（"持续观察群聊会被 WakingCheck 拦住"）**是错的**。

`astrbot/core/pipeline/waking_check/stage.py:174-259`：

```python
for handler in star_handlers_registry.get_handlers_by_event_type(
    EventType.AdapterMessageEvent, plugins_name=event.plugins_name,
):
    ...
    if passed:
        is_wake = True          # ← :232  插件 filter 通过 = 唤醒
        event.is_wake = True
        ...
if is_wake:
    self._umo_auto_name_recorder.schedule(event)
else:
    event.stop_event()         # ← :259  没有任何 handler 命中才丢弃
```

**结论**：只要插件注册了一个 `@filter.event_message_type(EventMessageType.ALL)` 的 handler，**任何群消息都会存活到 ProcessStage**，不需要 @、不需要 wake_prefix、不需要改白名单配置。

**但要注意一个关键区别**（同样是这一段代码）：

| 变量 | 何时置 True | 影响 |
|---|---|---|
| `event.is_wake` | @ / wake_prefix / 私聊 / **插件 filter 通过**（`:232`） | 决定事件是否被丢弃 |
| `event.is_at_or_wake_command` | 仅 @ / wake_prefix / 私聊（`:128` `:149` `:158`） | **决定主 Agent 是否运行** |

**插件把 `is_wake` 拉起来，但不会把 `is_at_or_wake_command` 拉起来。**

### 1.2 「不惊动主 Agent」是免费得到的

`astrbot/core/pipeline/process_stage/stage.py:52-66`：

```python
if not self.ctx.astrbot_config["provider_settings"].get("enable", True):
    return

if (
    not event._has_send_oper            # 插件没发过消息
    and event.is_at_or_wake_command     # 且这条不是 @ / 唤醒 / 私聊
    and not event.call_llm
):
    if (event.get_result() and not event.is_stopped()) or not event.get_result():
        async for _ in self.agent_sub_stage.process(event):
            yield
```

由此得出两条硬规则：

- **群聊里非 @ 的消息**：`is_at_or_wake_command == False` → **主 Agent 根本不跑**，你的插件是唯一处理者。这正好是"持续观察群聊"要的语义。
- **@ 消息**：主 Agent 默认会跑。若要由插件完全接管，**光 `event.stop_event()` 不够** —— 看 `:63` 那个 `or not event.get_result()` 分支，只 stop 不产生 result 时主 Agent 依然会跑。必须满足其一：
  - 产生过发送操作（`_has_send_oper` 变 True），或
  - `stop_event()` **且** `event.get_result()` 非空（yield 了东西）。

> 这条是最容易踩的坑，会表现为"我明明 stop 了，主 Agent 还是回了一句"。

### 1.3 后台常驻任务的正确写法（不是 `register_task`）

`astrbot/core/star/context.py:881-894`：

```python
@deprecated(reason="Start background tasks in the plugin's initialize() method instead.")
def register_task(self, task: Awaitable, desc: str) -> None:
```

**已弃用。** 正确姿势是在 `Star` 子类里实现 `async def initialize()`，在里面 `asyncio.create_task(...)`，并在 `async def terminate()` 里取消。

这对我们极其有利：**Router 的常驻循环和 Watchdog 的 60s 心跳，都放在 `initialize()` 里起，天然常驻，且插件热重载时能被干净地收掉。**

| 持久化 | 自己写到 `data/` 下（插件约定：数据不要放插件目录，见官方开发原则第 3 条）。格式建议 `data/super_bot/threads.json`，写入用 temp+rename 原子替换。 |

### 2.3 `router.py` —— 常驻 Router 会话（文章 2.1）

| 项 | 内容 |
|---|---|
| 接入点 | `async def initialize()` 里 `asyncio.create_task(self._router_loop())` |
| 依赖 API | `self.context.provider_manager.get_using_provider_async(...)`（`astrbot/core/star/context.py:497`）；`provider.text_chat(...)`（`astrbot/core/provider/provider.py:100`）；会话用自己的 `list[Message]` 维护，**不走** `conversation_manager` 的 UMO 绑定 |
| 关键设计 | Router 的上下文**必须自己持有**（一个 `list[Message]`），而不是依赖 `conversation_mgr`。原因：`conversation_mgr` 的模型是"一个 UMO 一个会话"，而 Router 恰恰要**不属于任何 UMO**——这是文章第 2 节的核心，也是唯一需要绕开框架约定的一处。 |
| batching | 用 `asyncio.Queue` 收 trigger；`await queue.get()` 之后 `asyncio.sleep(0)` 把队列里已有的全部取出，合并成一次 prompt。这就是文章 2.1 的批处理，纯 asyncio，10 行。 |
| 改动量 | 中（~250 行）。 |
| 风险 | 中。Router 用轻量模型即可（文章原话"常常没有想象中复杂"），但**别给它工具**（文章：可以不配 Bash）。 |
| 验收 | Router 单轮耗时随积压增长远慢于线性（对标文章 7.2：batch 1.0→2.8 时单请求仅 2.5s→3.9s）。 |

### 2.4 `worker.py` —— 隔离 Worker + 自己的小 ReAct loop（文章 2.2）

| 项 | 内容 |
|---|---|
| 接入点 | Router 决策后 `asyncio.create_task(self._run_worker(task))`，或 thread 直通时直接起 |
| 依赖 API | `provider.text_chat(prompt=, contexts=, system_prompt=, func_tool=ToolSet, tool_calls_result=ToolCallsResult, model=, tool_choice="auto")` → `LLMResponse`（`astrbot/core/provider/provider.py:100-137`）。**`func_tool` + `tool_calls_result` 这一对参数就是自建工具循环的全部所需。** |
| 循环形态 | `text_chat` → 若 `LLMResponse` 带 tool_calls → 本地执行 → `text_chat(tool_calls_result=...)` → 重复，直到无 tool_calls。约 80 行。 |
| 上下文隔离 | 每个 Worker 独占一个 `list[Message]` + 独占一个任务 id，互不可见。 |
| 模型选择 | `model=` 参数可按 Worker 覆盖 → 对应文章"Worker 配最强模型、Router 用轻量模型"。 |
| 改动量 | 中偏大（~350 行，含工具注册与错误处理）。 |
| 风险 | 中高。工具执行的错误处理、超时、循环上限必须自己兜（核心的 `astr_agent_run_util.py` 有一份可抄的循环，但它是私有的）。 |
| 验收 | 单 Worker 工具循环可跑通；超时与循环上限触发熔断。 |

> **⚠ 已排除：SubAgent 编排（`HandoffTool`）不能承载 Worker —— 它没有上下文持久化。**
>
> 三条铁证（v4.28.1 实读）：
>
> 1. `astrbot/core/agent/agent.py:9-15` —— `Agent` 是个只有 5 个**静态**字段的 dataclass（name / instructions / tools / run_hooks / begin_dialogs），**没有消息存储**。`SubAgentOrchestrator.reload_from_config()` 在配置重载时一次性建好这些对象，之后不可变。
> 2. `astrbot/core/astr_agent_tool_exec.py:307-385` `_execute_handoff()` —— 进去先 `contexts = None`，**只在有 `begin_dialogs` 时才填充**；然后是 `ctx.tool_loop_agent(prompt=input_, contexts=contexts, ...)`。也就是说：**父会话的历史一个字都不传，只传本次 `input` 字符串。**
> 3. 同函数末尾 `yield CallToolResult(content=[TextContent(text=llm_resp.completion_text)])` —— **只回最终文本**，子 agent 内部产生的多轮消息**全部丢弃**，没有任何地方写回 `tool.agent`。
>
> **结论**：每次 handoff 都是一次"静态前奏 + 本次输入"的**无记忆单次调用**。Thread 订阅语义要求"同一 Thread 的后续事件投给同一个 Worker，Worker 带着既有上下文继续推进"——用 handoff 会表现为：重犯已排除的方案、重复已做过的排查、忘记上轮结论。**不能当 Worker。**
>
> **正确的落点：直接调公开 SDK 的 `Context.tool_loop_agent()`**（`astrbot/core/star/context.py:215`，`.. versionadded:: 4.5.7 (sdk)`），它接受 `contexts: list[Message]`。**插件自己持有那个 `contexts` 列表**，每轮追加"用户输入 + 最终回复"并落盘 —— 于是既得到持久上下文的 Worker，**又不用自己写 ReAct 循环**（省掉自建 loop 那 350 行）。
>
> 两个必须知道的上限：
> - **必须传一个 `event: AstrMessageEvent`**（`:218`，关键字但必填）。Watchdog 或定时器发起、没有真实事件时，需要暂存"该 UMO 最近一个 event"或构造合成事件。**这是本期唯一需要额外设计的地方。**
> - **只返回 `LLMResponse`**，不给你中间消息。所以持久化只能是**回合级**（用户输入 + 最终回答），工具调用的中间细节丢失。对"接着干同一件事"够用，对"复盘每一步做了什么"不够——后者需要插件自己在工具层记录。

## 4. 三个真实风险

### 4.1 主动消息的平台矩阵

`astrbot/core/star/context.py:633` 源码注释：

> `qq_official(QQ 官方 API 平台) 不支持此方法。`

`Context.send_message(session=umo, message_chain=...)`（`:614`）是 Worker 完成后回投结果的唯一途径。平台选错，Worker 干完活只能等用户下次说话 —— **这正是《为人民服务》里 `pending` 队列等下一次 `chat.message` 的老坑**。

| 平台 | 主动消息 |
|---|---|
| aiocqhttp（QQ 个人号）/ Telegram / 飞书 / 企微 | 支持 |
| QQ 官方接口 | **不支持** |

**结论：主战场必须选 aiocqhttp 或 Telegram。**

### 4.2 一次 `stop_event()` 不够

见 §1.2。要彻底接管 @ 消息，必须 `stop_event()` **加上** 产生发送操作或 yield result。建议封装成一个 `self._swallow(event)` 辅助函数，全项目只走这一个出口。

### 4.3 插件热重载会丢内存状态

AstrBot 的插件是运行时注入 + WebUI 可热重载。**任何 Router 上下文、订阅表、Worker 状态，都必须落盘或可重建**，否则一次重载全部蒸发。

好消息：这正是《为人民服务》的强项 —— 你本来就是全文件系统状态（`state.json` / `mailbox/{agent}/` / `tasks/{id}.json`）。**这套落盘纪律原样搬过来即可，而且这次它真的有必要。**

## 5. 分期计划与验收

| 期 | 做什么 | 依赖 | 验收 | 回滚 |
|---|---|---|---|---|
| **P0** | 骨架：`main.py` + `metadata.yaml` + `_conf_schema.json`，通配 handler 只打日志 | 无 | 装进 `data/plugins/`，群消息在日志里可见，主 Agent 不被打扰 | 删目录 |
| **P1** | **skills 移植**：20 个 SKILL.md → `skills/` | P0 | WebUI `插件 → 技能` 出现 20 条，来源为该插件 | 删 `skills/` |
| **P2** | **watchdog**：`initialize()` 起 60s 循环 + 升级表 | P0 | 人为卡死任务，60s 内发现并升级 | 关配置开关 |
| **P3** | **thread 直通**：单平台 + 单指纹 | P0 | 同 Thread 后续事件直投，Router 决策数下降 | 删订阅表 |
| **P4** | **Router**：常驻会话 + asyncio 批处理 | P1 P3 | 批处理放大后单请求耗时增长远慢于线性 | 关 Router，退回主 Agent |
| **P5** | **Worker**：`Context.tool_loop_agent()` + 插件自持 `contexts`（**不用** SubAgent 编排） | P4 | 单任务全流程闭环 + 熔断 + 重载后上下文不丢 | 关 Worker，退回单层 |

**建议顺序：P0 → P1 → P2 → 停。** 先用真实的 2~3 个常驻任务跑一周，再决定 P3/P4/P5 的形态。这一步是从《为人民服务》学到的最贵的一课——**为了架构而架构，会在你还不知道要它干嘛的时候先把复杂度付了。**

### 5.1 难度重估：降的是什么，升的是什么

插件路线让**平台层**（plumbing）塌掉了，但**并发与状态层**比 OpenCode 时代更难。

| 层 | 以前（OpenCode / 2026-05） | 现在（AstrBot v4.28.1 插件） |
|---|---|---|
| 事件入口 | 无（只能靠人发消息） | `event_bus` + 9 阶段 pipeline + 平台适配器 —— **白送** |
| 多信道输出 | 无 | `send_message(umo, chain)` + 平台矩阵 —— **白送** |
| 异步 | `promptAsync` 未公开 + `sleep 2s` 赌父会话 | `initialize()` 里 `create_task` —— **白送** |
| ReAct 循环 | 自己写 | `Context.tool_loop_agent()`（公开 SDK，带 tools/contexts/max_steps/timeout）—— **白送** |
| 经验沉淀 | 自建 skill 体系 | 插件 `skills/` 自动进 Skill Manager —— **白送** |
| 配置界面 | 手写 JSON + 无校验 | `_conf_schema.json` → WebUI 表单 —— **白送** |

## 7. 参考实现：`deepseek-ai/dsh-superagent-prototype`

> **许可证 MIT** —— 这是它能当参考、而 AstrBot 只能当宿主的关键区别。代码、提示词、文档都可合法借鉴。
> 2026-10-31 新建，一天内 1,171★ / 90 fork，TypeScript，以 `cordis.patch.yml` 形式挂在 DSH 上（是 bundle 不是独立服务）。

**它实际是什么**（README 原文）：面向**单个 GitHub 仓库**的主动式编码 agent —— 监听 GitHub（可选飞书）→ 有人请求时开一个 work item → 在**自己的 session 和目录**里干 → 在**原会话**里回复（例如 PR）→ Web 面板展示"需要人做什么"。

README 的自我限定很重要，别把它当文章的实现检验：

> We have adapted it for publication, so it is **not identical to our internal version or the implementation described in the article**. **Some designs discussed in the article are directions for future development and are not implemented in this prototype.**

### 7.1 领域模型：最大的一件可迁移资产（`docs/001-domain.md`）

它把文章里含糊的地方全部落成了带规则的概念。**这套词汇直接决定你 Python 侧的数据类与状态机。**

```
Source → Trigger → Thread → Eval(Gate→Assessment) → Decision
                                     ↓ accept
                        Ticket(Mandate) → Assignment → Executor
                                     ↓
                                  Channel（回写）
```

| 它的概念 | 中文 | 你《为人民服务》里的对应物 | 它定的关键规则 |
|---|---|---|---|
| Source | 来源 | 平台适配器 | **持有自己的读取位置**（重启不重放事件）；把自己发的消息和范围外 Trigger 在入域前就丢掉 |
| Trigger | 触发 | 一条环境事件 | **不可变 + 幂等**（"同一个 Trigger 接受两次只产生一个 Ticket"） |
| Thread | 线程 | 无（你缺这个） | **同一 Thread 同时最多一个 Eval**，期间到达的 Trigger 合并进下一批 |
| Eval = Gate + Assessment | 评估＝准入＋研判 | 国务院的"要不要立项" | Gate 是确定性代码层，Assessment 是模型层；**Eval 不持状态** |
| Decision | 决定 | 立项/驳回 | `accept` 接单 / `stop` 停止 / `ignore` 忽略 / `unavailable` 未完成 |
| Mandate | 授权 | 红头文件 + 立项批文 | **不可变**：更宽 scope ＝ 新 Ticket；只有人能撤回；Policy 不再成立则吊销；结束时重校验 |
| Ticket | 工单 | 工作组 | **自己定义状态，不跟随 Executor 的 Session 状态**（可被换手、恢复、多个 Executor 跑过） |
| Assignment | 派工 | 派部委 | `pending → running → ended`，与 Ticket 独立演进 |
| Subscription | 订阅 | 无（你缺这个） | Thread 持有的**多对多**关系；匹配的 Trigger 扇出给所有活着的 Ticket，**不检查是谁发的**；人的消息经此到达 Ticket 时**不经过 Eval** |
| Channel | 渠道 | 输出信道 | Thread 的写侧；一个 Thread 可有多个 Channel |
| Policy | 策略 | 红线 + 各部委权限 | **版本化**；变更**不取消**正在跑的工作，只记录并投递 |
| Attention | 待人工决定 | 呈报用户 | 结构化的"在等人"，**不许用自由文本推断** |

两条最值得抄的判据：

- **Correlation 只加上下文，不路由；Subscriptions 才路由。**（你当年所有消息都经国务院，就是把路由和上下文混在了一起。）
- **`Rejected concepts` 表** —— 比正面定义更贵。它替你否掉了十几个迟早会踩的设计：跨 Source 身份映射、Eval 自己排延迟 Trigger、"一个 Thread 只允许一个活 Ticket"、Correlation 承担路由、用报告的散文推断"在等人"、Policy 变更时取消在跑的工作……

### 7.2 三档可抄，成本从低到高

### 7.4 一个哲学对照（值得写进你的设计原则）

README 的原话：

> it **acts only when asked or when a rule the team wrote allows it**, and **speaks only when someone must act or can use a result**.

你当年的"不空转 / 停机令 / 禁止写 Todos"，是同一个诉求的**禁令式**表达；它的是**准入式**表达。

## 10. 架构判定：两条循环（与 IM、工期无关）

### 10.1 "插件不能自发事件"不是障碍

核查结论：

- `astrbot/core/event_bus.py:39` 的 `EventBus.dispatch()` **无参数**，从内部队列取事件 —— **没有公开的事件注入入口**。
- 但 core 自己也不注入。`astrbot/core/astr_agent_tool_exec.py:517-601` 的 `_wake_main_agent_for_background_result` 做法是：
  1. 构造一个 **`CronMessageEvent`** 当身份/配置载体（**不是**投进 pipeline）；
  2. `_get_session_conv(event=cron_event, ...)` 拿到该 UMO 的会话；
  3. `req.contexts = json.loads(conv.history)` —— **从 DB 读持久上下文**；
  4. 把结果塞进 `system_prompt`，**直接调 agent runner**。

**即：绕过 pipeline，直接调用 agent 循环。** 所以正确架构不是"往 pipeline 里塞事件"，而是**两条并行的循环**：

```
Path A（反应式，走 pipeline）
  平台事件 → 9 阶段过滤 → 插件 Gate → 主 agent（AstrBot 原生，上下文由 DB 管）

Path B（主动式，不走 pipeline）
  Sources → Trigger Queue → Router loop → Worker loop(s) → Outbox → send_message
                                    ↑
                            上下文由插件自持

两路共享：store（Thread / Ticket / Mandate）、skills、provider、日志
```

**关键洞察：Router 根本不需要"被事件唤醒"——它自己就是一个永远在跑的循环，从队列里取活。** 这既绕开了原语缺失，也不与 AstrBot 对抗：pipeline 服务反应式，你的循环服务主动式。

### 10.2 最大红利：上下文 100% 归你

`Context.tool_loop_agent(contexts=list[Message])` 让插件精确控制窗口里每一个 Message。文章 3.3 的 Inline & Spill 在这里从"设计原则"变成**完全可控的实现** —— 比 DSH 里更直接（DSH 的上下文归 session）。

### 10.3 三个架构级难点（不是工程问题）

| 难点 | 说明 |
|---|---|
| **取消** | `tool_loop_agent` 是一次 await。中途 stop ＝ `task.cancel()` + 状态机必须有 `cancelled` 路径 + 清理。文章没讲，参考实现有 Assignment 的 `ended`。 |
| **两套体系的边界** | 主 agent（Path A）与插件编队（Path B）并行。**谁在何时接管必须写成明确规则**，否则同一件事被两边各干一遍，用户收到两条互相矛盾的消息。这正是当年"不空转/停机令"想解决却没解决的——因为那时两边其实是同一套。 |
| **Watchdog 的覆盖范围** | 插件内的 Watchdog 与 Router 同进程，进程假死时一起挂。进程级自愈归 core 的 `process_restart.py`。**它只能管"任务级停滞"，管不了"系统假死"** —— 分工不是缺陷，但边界要清楚。 |

### 10.4 一个插件补不了的硬缺失

**AstrBot 没有 per-task 执行环境隔离。** DSH 的原型明确写着 "one Executor Session and **one directory per Ticket**" —— 所以它能真并行改代码。AstrBot 的 `workspace.py` 是它自己的概念，插件拿不到"为每个任务起隔离目录并在其中执行工具"的能力。

后果取决于 Super-bot 干什么：

- **信息型助手**（读群、判断、调度、回话、记档）→ 不需要隔离，载体完全够。
- **要并行写代码/改仓库** → 硬缺失。插件只能当调度层，执行器得外接（DSH / 独立 runner / 容器）。

### 10.5 一句话定位

**AstrBot 插件不是"降级版的 DSH"，而是另一种分工：**

| | DSH / 原型 | AstrBot 插件 |
|---|---|---|
| 控制权 | 不给（bundle / patch） | **全给你**（Python + 公开 SDK） |
| 上下文 | session 管 | **你管** |
| 执行环境 | per-Ticket 目录 | **没有** |
| 事件入口 | 自己写 Source | 平台适配器白送 |

**而"多任务编队 + 经验沉淀"依赖的是控制权与上下文，不是执行环境。** 所以这个载体对目标是够的——**只要你不需要它去并行改代码。**

## 11. Worker 的能力边界：MCP 与长上下文

结论：**Worker 不是缩水版，MCP 与长上下文都能配，而且长上下文那块比手写更强。**

### 11.1 MCP：一行拿到全部

```python
tools = self.context.provider_manager.llm_tools.get_full_tool_set()
llm_resp = await self.context.tool_loop_agent(
    event=event, chat_provider_id=prov_id, prompt=..., tools=tools, ...
)
```

| 事实 | 位置 |
|---|---|
| `get_full_tool_set() -> ToolSet` | `astrbot/core/provider/func_tool_manager.py:496` |
| MCP 客户端在核心启动时初始化，工具注册进同一个 manager | 同文件 `init_mcp_clients` `:540` |
| `Context.provider_manager.llm_tools` 就是这个 manager | `astrbot/core/star/context.py:358` |
| **MCP 工具外面包了权限守卫**，权限策略自动继承 | 同文件 `_PermissionGuardedTool` `:214` |

所以 Worker 天然拥有你配的全部 MCP 工具，不用逐个接。

### 11.2 长上下文：四层能力全在，且可注入自定义

`ToolLoopAgentRunner` 完整集成了上下文管理子系统：

| 能力 | 参数（均可从 `tool_loop_agent(**kwargs)` 传入，会**直接**转给 `runner.reset()`） |
|---|---|
| 按轮截断 | `truncate_turns`（默认 1） |
| LLM 压缩 | `llm_compress_instruction` / `llm_compress_keep_recent_ratio`（默认 0.15）/ `llm_compress_provider` |
| 自定义 token 计数 | `custom_token_counter` |
| 自定义压缩器 | `custom_compressor` |

每轮都会跑 `request_context_manager.process(...)`（`tool_loop_agent_runner.py:819`）。

### 11.3 重点：Spill 已经实现了 —— 文章 3.3 的一半是白送的

`tool_loop_agent_runner.py:369-455`：工具结果超过阈值 → **写进临时目录** → 上下文里只留**预览 + 路径** → 模型需要时用 `astrbot_file_read_tool` 读回。

而 `tool_loop_agent` 在 `context.py:302-308` 会**自动**检测 ToolSet 里有没有 `astrbot_file_read_tool`，有就自动配上 overflow dir。

**这就是文章 3.3 的 Spill，在工具层已经做好了。** 你只需要管 Inline 侧（注入什么），Spill 侧不用写。

> 注意：如果你自己挑工具而不是 `get_full_tool_set()`，记得把 `astrbot_file_read_tool` 带上，否则自动配置不生效。

### 11.4 但要把两件事分开：能力 vs 持久化

| | 谁负责 |
|---|---|
| **单次调用内的上下文管理**（压缩、截断、Spill） | ✅ **白送**，runner 自带 |
| **跨调用的上下文持久化**（把完整消息列表落盘） | ❌ **你的活** —— `tool_loop_agent` 只返回最终 `LLMResponse`，中间消息不交给你 |

默认只能存"回合级"（用户输入 + 最终答复），工具调用细节丢失。

**解法**：`tool_loop_agent` 接受 `agent_hooks: BaseAgentRunHooks`（`context.py:269`）。挂在每一步上自己攒完整消息列表并落盘，就绕开了这个限制。具体钩子签名看 `astrbot/core/agent/hooks.py`。

## 12. 补上两个缺口：取消 与 沙箱隔离

### 12.1 取消：官方已有一套，按 UMO 分桶

`astrbot/core/utils/active_event_registry.py`（94 行，全文读完）：

```python
class ActiveEventRegistry:
    _events: dict[str, set[AstrMessageEvent]]                          # umo → 活跃事件集合
    _agent_stop_callbacks: dict[AstrMessageEvent, Callable[[], None]]  # 事件 → 怎么让它停

    def register(event)                                   # 进 pipeline 时（scheduler.py:89）
    def unregister(event)                                 # 出 pipeline 时（:100）
    def register_agent_stop_callback(event, callback)
    def unregister_agent_stop_callback(event)
    def stop_all(umo, exclude=None) -> int                # 硬停：event.stop_event()，中断传播
    def request_agent_stop_all(umo, exclude=None) -> int  # 软停：设 extra + 调 callback，不中断传播
```

**两类语义的差别是源码注释明写的**：

> 与 `stop_all` 不同，这里**不会调用 `event.stop_event()`，因此不会中断事件传播，后续流程（如历史记录保存）仍可继续**。

| 方法 | 行为 | 适用 |
|---|---|---|
| `stop_all` | `event.stop_event()`，事件传播立刻中断 | 清场、重开 |
| `request_agent_stop_all` | 只设 `agent_stop_requested` 标记 + 调 callback，事件流继续 | **用户改主意，需保留收尾与历史** |

**主 agent 的标准做法**（`core/pipeline/process_stage/follow_up.py:43`）：跑 runner 时 `register_agent_stop_callback(runner_event, <cancel_fn>)`，`finally` 里 `unregister_agent_stop_callback`。`/stop` 指令（`builtin_stars/builtin_commands/commands/conversation.py:117-119`）和 WebUI 停止按钮（`dashboard/services/chat_service.py:1212`）都走这个口。

**插件该怎么接**：

1. Worker 启动时用触发它的那个 event 作 key，`register_agent_stop_callback(event, worker.cancel)`；
2. `worker.cancel()` 内部 `task.cancel()`（asyncio 协作式取消）；
3. Worker 必须 `except asyncio.CancelledError:` 里收尾——清理 MCP 在途调用、写终态 `cancelled`、向 Router 汇报——**再 `raise`**，否则取消会被吞掉；
4. 结束时 `unregister_agent_stop_callback`。

**白送的用户体验**：接上之后，用户发 `/stop` 或点 WebUI 停止，能一并停掉后台 Worker。不接的话，用户会发现"`/stop` 停不掉那些任务"。

**一个副作用（根因同 `tool_loop_agent`）**：callback 的 key 是 **event 对象**，registry 又按 `umo` 分桶。所以**定时发起、没有 event 的 Worker 登记不进去**——再一次指向"Worker 需要 event 作为身份载体"。

### 12.2 沙箱：能力比预想完整，接入层有坑

**事实**：

| 项 | 位置 |
|---|---|
| `computer_use_runtime` ∈ `none / local / sandbox` | `astr_main_agent.py:205` |
| booter 全家桶：`local` / `cua` / `boxlite` / `shipyard` / **`shipyard_neo`** / `bay_manager` | `core/computer/booters/` |
| 能力层：`filesystem` / `shell` / `python` / `browser` / `gui` | `core/computer/olayer/` |
| 沙箱客户端（会话、技能同步、空闲回收） | `core/computer/computer_client.py` |
| **handoff 子 agent 也会挂沙箱工具** | `astr_agent_tool_exec.py:199` `:268` |
| 插件提供的 skills 会自动同步进沙箱 | `computer_client.py:457-553` `_apply_skills_to_sandbox` |

**坑**：`_apply_sandbox_tools`（`astr_main_agent.py:1062`）与 `_build_handoff_toolset`（`astr_agent_tool_exec.py:250`）都是**私有函数**，只在主 agent / handoff 的构建路径被调用。`tool_loop_agent(tools=你传的 ToolSet)` **不会**自动给你挂沙箱工具。

**三条绕法**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 走 handoff / SubAgent 路径，沙箱工具自动挂上 | handoff **无上下文持久化**（§2.4 已排除） |
| B | `from astrbot.core.astr_main_agent import _apply_sandbox_tools` | 私有 API，随上游漂移 |
| **C（推荐）** | `get_booter(...)`（`computer_client.py:553`，**模块级公开函数**）拿到 `ComputerBooter`，自己包成 `FunctionTool` 塞进 ToolSet | 多写一层工具包装，但可控 |

**为什么推荐 C**：它正好补上"没有 per-task 目录隔离"这个缺口——**你要的隔离，本质上就是"每个 Ticket 一个 booter 实例"**。而 `get_booter` 是模块级函数，不算私有 API。

**额外红利**：沙箱会同步插件 `skills/`（`_apply_skills_to_sandbox`）。所以你把 20 个 SKILL.md 放进插件目录，**沙箱里的 Worker 也看得到** —— 经验沉淀与执行环境是打通的。

### 12.3 结论

| 缺口 | 状态 |
|---|---|
| 取消 | **白送**。接 `ActiveEventRegistry` 即可，且自带 `/stop` 与 WebUI 打通 |
| per-task 目录隔离 | **可补**。`get_booter()` + 自己包工具，每个 Worker 一个 booter |

## 13. 沙箱选型：Shipyard Neo（`AstrBotDevs/shipyard-neo`）

> Python · **AGPL-3.0** · 91★ / 25 fork / 13 open issue · 2026-01 创建 · 最近推送 2026-10-16
> 一句话：**"计算与存储分离"的沙箱基础设施** —— 正好是文章 5.1 那件事的现成实现。

### 13.1 它的领域模型，几乎逐条对上你的需求

| 它的概念 | 定义 | 对你的意义 |
|---|---|---|
| **Sandbox** | 对外唯一的计算资源单元，**稳定 ID**，聚合 Profile / Cargo / Session，支持 TTL | **= 你的一个 Ticket**。客户端只认这个 ID |
| **Session** | 一组运行中的容器实例，**可能被系统回收/重建，但对 Sandbox 客户端透明** | 容器挂了重开，你的 Worker 不用知道 |
| **Cargo** | 持久化存储卷，固定挂 `/workspace`，跨 Session 共享 | **工作目录不丢** —— 补上"上下文我存、工作区 Cargo 存"的另一半 |
| **Profile** | 容器拓扑、资源限制、能力集合（python/shell/filesystem/browser）、空闲回收策略 | 每个 Ticket 可以配不同规格 |

三个数据面：**Ship**（Python / Shell / Filesystem / Terminal，工作区固定 `/workspace`）、**Gull**（浏览器，`agent-browser` CLI 转 HTTP）、**Cargo**（卷）。

**关键结论：一个 Ticket 一个 Sandbox = 你要的 per-task 隔离，而且是持久化的。**

### 13.2 三条接入路径（都不碰 AstrBot 私有 API）

| 路径 | 说明 |
|---|---|
| **Bay REST API v1** | Sandboxes（创建/查询/续 TTL/保活/停止/删除）、Capabilities（python / shell / filesystem / browser）、History、Skills |
| **Python SDK** | 仓库自带 `shipyard-neo-sdk/` |
| **MCP Server** | 仓库自带 `shipyard-neo-mcp/` —— 可以只当 MCP 挂进 AstrBot，零代码 |

`Bay` 还负责**幂等与 GC** —— 重复创建同一个 Sandbox 不会出两份，这是你自己写沙箱最容易漏的。

### 13.3 意外收获：它的 Skills 自迭代 ≈ 你的"红头 → skill"自动化版

README §6：

- **执行证据层**：每次 Python / Shell / Browser 执行自动生成并持久化 `execution_id`
- **技能控制面**：`Candidate → Evaluation → Release（canary / stable）→ Rollback`
- **自动发布**：score ≥ 0.85、replay_success ≥ 95%、samples ≥ 30 → 发 canary，健康 24h 升 stable
- **自动回滚**：success_rate 降 >3% 或 error_rate 升 >2x → 回滚
- 熔断开关 `BAY_BROWSER_AUTO_RELEASE_ENABLED`

对照你的《为人民服务》：

| | 你的做法 | 它的做法 |
|---|---|---|
| 触发 | 部委自我批评（人工写） | 执行证据自动沉淀（`execution_id`） |
| 审议 | 档案局九维索引 + 交叉分析 | Evaluation（指标驱动） |
| 签发 | 国务院签红头 | `Release` canary → stable |
| 回滚 | 无（红头发了就发了） | 指标劣化自动回滚 |
| 学习 | 部委读红头、提炼 skill | Promote 后进 Skill 库 |

**你的是"人类审议制"，它的是"指标驱动制"。同一件事的两个极端。** 前者上限高（能处理语义问题），后者可靠（不依赖人肯写自我批评）。

### 13.4 四个必须知道的代价

| 代价 | 说明 |
|---|---|
| **AGPL-3.0** | 与 AstrBot 相同。**作为独立服务调用**（不修改、不内嵌分发）通常不触发传染；改它并对外提供则有义务。 |
| **项目很新** | 2026-01 创建，91★、13 open issue。浏览器自动发布那套策略看着激进，官方自己留了熔断开关 —— 别当成熟基础设施依赖。 |
| **部署门槛最高** | Bay 要挂 `docker.sock`、管 Ship 容器、用 `container_network` 模式（容器 IP 直连，**不向宿主机暴露端口**）。**Windows 上能否跑通需先验证**（Docker Desktop + volume/socket 挂载）。 |
| **并发上限取决于部署** | 见 §13.7 —— **不是 ship 数量上限**。旧版 bay 才有 `MAX_SHIP_NUM`；Neo 的限制来自 Profile 资源限额 × 宿主机总量，以及 TTL/空闲回收。 |

另外：AstrBot 的 `compose-with-shipyard.yml` 里 bay 的 `8156` 端口是**注释掉的**（走 docker 内网）。若插件不在同一网络（例如 AstrBot 跑在 Windows 宿主），需自行暴露端口 + 配 `ACCESS_TOKEN`。

### 13.5 务实建议：先抽象，后切换

**不要让"沙箱是否部署好"卡住 Worker 的开发。** 在插件里定义一个端口：

```python
class SandboxPort(Protocol):
    async def create(self, ticket_id: str) -> str: ...   # → sandbox_id
    async def exec(self, sandbox_id: str, code: str, lang: str) -> dict: ...
    async def destroy(self, sandbox_id: str) -> None: ...
```

- **阶段一**：本地实现（临时目录 + subprocess），Worker 逻辑先跑通；
- **阶段二**：换成 Bay HTTP 实现（或直接挂 `shipyard-neo-mcp`）。

这正好对上它文档里那句：**"Session 可能被系统按策略回收/重建，但对 Sandbox 客户端透明"** —— 你的 `SandboxPort` 就是这个客户端。

### 13.6 一个必须配套的动作

**取消 Worker 时必须回收沙箱。** 否则 `task.cancel()` 只是停了客户端 await，容器还在跑并占配额。取消路径要写成：

```
task.cancel() → except CancelledError → await sandbox.destroy(id) → 写终态 cancelled → report to Router → raise
```

漏了这一步，取消等于没取消，而且会在 `MAX_SHIP_NUM=10` 的配额下迅速把池子堵死。

### 13.7 更正：并发上限不是 ship 数量（此前误判）

**先说错在哪**：`MAX_SHIP_NUM=10` / `DEFAULT_SHIP_CPUS` / `BEHAVIOR_AFTER_MAX_SHIP=reject` 是**旧版 bay**（`soulter/shipyard-bay`）的 compose 默认值，**不是 Neo 的模型**。AstrBot 里两套 booter 并存：`core/computer/booters/shipyard.py`（旧，8KB）与 `shipyard_neo.py`（新，24.7KB）—— 我把旧版的全局配额当成了 Neo 的上限。

**Neo 的真实层级**（`doc/bay_abstract_entities.md`）：

```
1 × Bay（控制面）
 └─ N × Sandbox（稳定 ID，客户端持有）
     ├─ 1 × Session（临时容器组，可被 GC 回收/重建）
     │   └─ 1..N × Container（Phase 1 单容器；Phase 2 多容器协作）
     └─ 1 × Cargo（持久卷，固定挂 /workspace）
```

**真正的限制来自三处**：

1. `ProfileConfig` 的资源限额（CPU / 内存）与**空闲回收时间**；
2. `Driver`（单机 Docker / K8s 集群）与宿主机（或集群）的实际余量；
3. GC：空闲 Session 被回收，过期 Sandbox 被清。

**由此得到一条对设计很重要的结论：**

> **真实的并发上限 = 同时 `RUNNING` 的容器数，不是 Sandbox 总数。**

因为 Session 空闲会被回收、下次用时 `ensure_running` 幂等重建，而**这一切对客户端透明**。所以 Bay 天然允许"超订"：你可以有几十个逻辑 Worker（Ticket），同时只有几个容器在真跑。

**这正好对上文章的职责划分**：

| | 逻辑存在 | 物理占用 |
|---|---|---|
| Router | 一个常驻会话，始终"在" | **不占容器** |
| Ticket / Worker | 可以有几十个 | 只有正在执行的那几个占容器 |
| 空闲中的 Ticket | 状态在磁盘上 | 容器被 GC 收回 |

**所以你要调度的是"RUNNING 容器数 × 每个 Profile 的资源"，不是"ship 数"。** 这也意味着：Worker 的状态必须能"从磁盘重建"，而不能指望进程或容器还在 —— 与 §9 第 5 条（Ticket 状态不跟随 Executor）互为印证。

### 13.8 两个可以直接抄的设计细节

**一、状态实时计算，不存字段。**
`Sandbox` 的 `IDLE / STARTING / READY / FAILED / EXPIRED / DELETED` **不是存储的字段，而是根据当前 Session 状态实时算出来的**。这样永远不会出现"Sandbox 说 READY 但容器早死了"的不一致。

> 你的 `Ticket` / `Assignment` 状态也该这么设计：**存事实（事件、时间戳、最后一步），状态是算出来的**。这一条能省掉你未来 80% 的状态不一致 bug。

**二、期望态 vs 观察态。**
`Session` 用 `Desired` vs `Observed` 双状态管理（`PENDING / STARTING / RUNNING / DEGRADED / STOPPING / STOPPED / FAILED`）。`DEGRADED` 这个态尤其值得注意——它是"没死但不健康"，正是你当年监委要抓的那种"看起来在跑其实没进展"。

**三、Cargo 有 External 类型。**
`Managed`（随 Sandbox 生灭）与 **`External`（独立存在，可被多个 Sandbox 同时挂载）**。后者意味着**多个 Worker 可以共享同一个工作区**——正好对应文章说的"多个 Worker 订阅同一 Thread、在共享环境里自行发现冲突"。

### 附：一个白捡的能力

`HandoffTool.default_parameters()` 里有个 `background_task: boolean`（`astrbot/core/agent/handoff.py:51-58`），配上 `astr_agent_tool_exec.py:388-428` 的 `_execute_handoff_background` 与 `:431-475` 的 `_wake_main_agent_for_background_result` —— **后台子任务跑完自动唤醒主 Agent**，注释里写着 "the same pattern used by `_execute_background`"。

这就是文章 4.1 的全双工异步 ReAct，**AstrBot 已经原生实现了**，而且是"后台完成 → 作为新事件投回会话"的完整闭环。当年你在 OpenCode 上要靠 `promptAsync` + `sleep 2s` + `pending` 队列硬凑的东西，这里是核心自带。
